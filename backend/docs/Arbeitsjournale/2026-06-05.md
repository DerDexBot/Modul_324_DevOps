### 2. CD-Pipeline eingerichtet

Wir haben die bestehende CI-Pipeline um eine Continuous-Delivery-Stufe erweitert.

**Dockerfile** (`backend/Dockerfile`): Minimales Image auf Basis von `eclipse-temurin:21-jre-alpine`. Das von Maven gebaute JAR wird ins Image kopiert und beim Containerstart ausgeführt.

**CD-Pipeline** (`.github/workflows/cd.yml`): Wird automatisch gestartet, sobald die CI-Pipeline auf `main` erfolgreich abgeschlossen hat (`workflow_run`-Trigger). Die Pipeline baut das JAR mit `mvn package -DskipTests`, loggt sich bei der GitHub Container Registry (`ghcr.io`) ein und pushed das Docker-Image mit zwei Tags:
- `latest` — immer das aktuellste Image
- `sha-<commit>` — eindeutige Version pro Commit für Rollbacks

Die CD-Pipeline wurde getestet und das Image ist unter `ghcr.io/derdexbot/todo-backend` abrufbar.

**CD-Dokumentation** (`backend/docs/CD/cd-dokumentation.md`): Erklärt den Unterschied zwischen CI, Continuous Delivery und Continuous Deployment, den Ablauf der Pipeline, das Dockerfile Schritt für Schritt sowie die Image-Tags und wie das Image lokal gestartet werden kann.

### 3. Frontend-Features via Kanban-Workflow implementiert

Wir haben drei Issues auf GitHub erstellt und jeweils in einem eigenen Feature-Branch umgesetzt:

#### US-19: Frontend Redesign (Issue #19 → Branch `feature/issue-19-frontend-redesign`)

Das bisherige Design war funktional, aber optisch wenig ansprechend. Wir haben `App.css` und `index.css` vollständig überarbeitet:

- Heller Hintergrund mit Indigo-Farbverlauf
- Weisse Karten mit feinem Schatten
- Indigo (`#4f46e5`) als Primärfarbe für Buttons und Akzente
- Erledigte Tasks erhalten automatisch einen grünen Hintergrund via CSS-Klasse `done`
- Hover-Effekte auf Task-Einträgen und Buttons
- Modernerer Font-Stack (System UI)

#### US-20: Filter Alle / Offen / Erledigt (Issue #20 → Branch `feature/issue-20-filter`)

Neue clientseitige Filterfunktion:

- State `filter` (`'all' | 'open' | 'done'`) in `App.jsx`
- `filteredTodos` wird per `.filter()` aus der vollständigen Liste berechnet
- Filter-Buttons mit Anzahl erscheinen sobald Tasks vorhanden sind
- Aktiver Filter ist durch Indigo-Hintergrund hervorgehoben
- Kein zusätzlicher Backend-Aufruf nötig

3 neue Jest-Tests decken alle Filter-Szenarien ab.

#### US-21: Fortschrittsanzeige (Issue #21 → Branch `feature/issue-21-fortschritt`)

Neue Fortschrittsanzeige über dem Formular:

- Zeigt „X von Y Aufgaben erledigt"
- Fortschrittsbalken füllt sich proportional mit Indigo-Gradient
- Bei 100% erscheint „🎉 Alle Aufgaben erledigt!"
- Wird ausgeblendet wenn keine Tasks vorhanden sind
- Berechnung rein frontend-seitig: `doneCount / totalCount * 100`

3 neue Jest-Tests prüfen den Fortschrittstext, die Glückwunsch-Meldung und das Ausblenden.

## Erkenntnisse / Lerngewinn

- **Continuous Delivery vs. Deployment**: Der Unterschied ist klar geworden — CD endet bei uns beim Image-Push, nicht beim Deployment auf einen Server. Das ist für das Schulprojekt der richtige Umfang.
- **`workflow_run`-Trigger**: Durch diesen Trigger in GitHub Actions wird sichergestellt, dass die CD nur läuft wenn CI grün ist — eine wichtige Qualitätssicherung.
- **GitHub Container Registry**: Kostenlos für öffentliche Repositories, direkt integriert, kein externer Dienst nötig. Der `GITHUB_TOKEN` reicht für den Push.
- **Kanban und Issues**: Die Kombination aus GitHub Issues, Feature-Branches und `Closes #XX` in Commit-Messages ermöglicht einen sauberen, nachvollziehbaren Workflow. Issues schliessen sich automatisch beim Merge.
- **Chained Branches**: Da die Features aufeinander aufbauen (Filter baut auf Redesign), haben wir die Branches sequenziell verkettet, um Merge-Konflikte zu vermeiden.
- **Frontend-Tests mit jsdom**: React-Komponenten können vollständig getestet werden ohne einen Browser oder Backend-Server. `userEvent` simuliert realistische Benutzeraktionen wie Klicks und Tastatureingaben.
